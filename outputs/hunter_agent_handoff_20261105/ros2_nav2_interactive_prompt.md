## 4. 总体推进阶段

### 阶段零：确认建图会话已结束
- 查看本人建图会话是否仍有传感器驱动、FAST-LIVO2 或 RViz 进程在运行。
- 必要时正常停止本人残留会话，保留本轮数据。
- 确保不重复启动同一硬件的驱动，不影响其他人的程序。

### 阶段一：只读探查现有导航资产
- 查找并确认：
  - `/home/car/hunter_nav_odom_ws` 是否存在，以及车上现有的 Nav2 包、Hunter 底盘驱动、机器人模型（URDF/Xacro）、Launch 脚本、参数文件和已有二维地图；
  - 师兄导航系统的实际启动顺序；
  - `use_robot` 等环境命令的具体定义，以及 `ROS_DOMAIN_ID`、RMW 实现、工作空间覆盖关系（Overlay/Underlay）；
  - CAN 接口、底盘反馈、里程计、控制话题，以及已有传感器驱动状态；
  - 梳理哪些内容可以直接复用，哪些只需要在个人目录 `~/hz_nav_ws` 里适配。
- **底盘运动学核对**：先核对 Hunter 具体型号和转向方式。若为阿克曼（Ackermann）前轮转向底盘，必须考虑最小转弯半径，绝不能直接按能够原地旋转的差速机器人配置。

### 阶段二：建立个人独立导航工作空间
- 检查并新建个人导航目录（如 `/home/car/hz_nav_ws`）。
- 安全复制必要的源码、配置、Launch 和地图副本到个人导航空间。
- 保留并复用已有传感器标定参数及原文件，不改动标定。
- 按实际需要在个人空间中完成编译（`colcon build`），解决个人工程中的依赖或配置问题。
- 明确验证每个软件包实际来自哪个工作空间，避免无意间运行师兄目录中的另一套配置。

### 阶段三：确定地图与定位方案
- **先解释并确认两个核心概念**：
  1. 已有的三维 PCD 点云地图不等于可以直接加载到标准二维 Nav2 导航中的栅格地图；
  2. 区分“里程计（Odometry）”与“地图定位（Localization）”：FAST-LIVO2 能输出实时位姿，不代表已经具备在历史保存地图中重新定位的能力。
- 优先检查师兄已有的二维栅格地图及 YAML 配置文件是否适合当前实验室场地。
- 若需要使用我采集保留的 PCD 地图（`lab_20261011_141011_768151` 或 `lab_20261011_155236_369289`），先在副本上评估转换二维地图及定位的可行性：
  - 转换时严格检查高度截取范围、地面去除、分辨率、原点坐标，以及占用（Occupied）、空闲（Free）、未知（Unknown）区域划分，**绝不能把没扫描到的未知区域直接当作可通行区域**。
- 如果评估后需要额外采集二维地图，先向我说明必要性，再由我决定，不直接要求重新建图。
- 标准二维地图加载方式严格以 **Nav2 Humble** 地图加载实现和本机实际版本为依据。

### 阶段四：检查导航所需接口与坐标关系
- 逐项检查并确认：
  - 地图数据、激光数据（或点云数据），以及实际使用的里程计话题；
  - 是否需要将 XT32 点云（`/lidar_points`）转换为 `/scan`；如师兄已有转换节点（如 `pointcloud_to_laserscan`），先复用并核对过滤参数；
  - 检查地面、车体自身和车载设备是否被错误当成障碍物；
  - 核对 `map → odom → base_link → 传感器` 的完整坐标变换关系（若实际使用 `base_footprint` 等中间坐标系，按现有模型核对）；
  - 查明每段 TF 分别由哪个节点发布，避免重复发布或缺失；**不要为了消除报错而随意发布虚假的静态 `map → odom` 或 `odom → base_link`**；
  - 检查里程计消息中的位置、速度、坐标系和时间戳是否合理（参考 Nav2 官方里程计接入要求，并以本机 Humble 实现为准）；
  - 核对导航是否需要继续运行 FAST-LIVO2、D435i 相机或外部 CH104 IMU（由实际定位与里程计方案决定，不默认把建图时所有节点全部打开）；
  - 核对 Hunter 底盘实际接受的控制消息类型，以及速度、角速度或转角的物理含义，**不能只看话题名字（如 `/cmd_vel`）就假定兼容**。

### 阶段五：配置 Nav2 并完成静态验证
- 在个人导航工作空间配置中逐项核对并带我理解：
  - 地图与定位、全局规划器（Planner）、局部控制器（Controller）、全局和局部代价地图（Costmap）；
  - 车体轮廓（`footprint`）、障碍膨胀半径、速度与加速度限制；
  - 最小转弯半径及阿克曼底盘运动约束；
  - 排查并禁用不适合该底盘的原地旋转（Spin）、原地朝向调整和恢复行为（Recovery Behaviors）；
  - 检查 Nav2 生命周期节点（Lifecycle Nodes）是否全部进入预期 `active` 状态。
- **安全隔离速度输出**：在实车运动获得我明确授权前，先将导航速度输出隔离重映射到不连接底盘的验证话题，并检查实际发布、订阅关系。
- **RViz 静态验证**：在 RViz 中检查地图、机器人位置、激光与墙体的重合情况、障碍物更新和路径规划结果。**明确不能仅凭“RViz 出现路径”就宣称导航成功**。

### 阶段六：现场低速导航与收尾（需现场条件满足且获我明确同意）
- 静态检查全部通过、现场有人员配合且取得我明确同意后，再按顺序逐步进行：
  1. 底盘控制方向和停止方式验证；
  2. 小范围、低速、单目标导航；
  3. 路径跟踪、转弯和障碍物处理检查；
  4. 取消目标、遥控接管及停车验证（**不要把取消目标或关闭终端等同于已经可靠停车，必须结合实际底盘反馈和现场观察确认**）；
  5. 正常结束本人的导航会话，保存日志和最终参数。
